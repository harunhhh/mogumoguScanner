# 🍛 もぐもぐスキャナー

料理の写真を撮るだけで、**AIが料理名を判定しカロリーを推定**する Web アプリです。

---

## 📸 デモ

| 入力 | 出力 |
|------|------|
| カメラ撮影 or 画像アップロード（ドラッグ＆ドロップ対応） | 料理名・確信度・推定カロリー (kcal)・目安量・予測候補 TOP3 |

**公開URL**: https://mogumogu-mauve.vercel.app

---

## ✨ 主な機能

- **撮影・アップロード**：スマホのカメラで撮影、または JPEG / PNG / WebP の画像をアップロード（ドラッグ＆ドロップ可）
- **料理名とカロリーの推定**：100種の料理から判定し、`food_calories.csv` のカロリー・目安量を表示
- **予測候補 TOP3 の表示**：各候補の確信度・カロリー・目安量を並べて表示
- **候補を選んで確定**：TOP3 の候補をタップすると、その料理を「あなたが選択」として確定し、料理名・カロリー・目安量がその候補の値に切り替わる
  - AI が「判定不能」とした場合でも、候補から選べばカロリーを表示できる
  - 選択中の候補をもう一度タップするか「選択を取り消して、AIの判定に戻す」を押すと、AI の判定表示に戻る
  - 新しい画像を解析すると選択はリセットされる
  - 候補は `button` 要素（`aria-pressed` 付き）で、キーボード操作・スクリーンリーダーでも選択できる
- **サーバー起動待ちの表示**：Render の無料プランはスリープするため、画面を開いた時点でバックエンドを起こしにいき、「起動待ち」と「解析中」を区別して経過秒数を表示

候補を選べるようにしたのは、実写での精度が Top-1 約60%・Top-3 75% で（下記「精度の実測と検証の経緯」を参照）、1位が外れても3位以内に正解が入っていることが多いためです。混同しやすい料理同士はカロリー差が大きい（ラーメン 500 / チャーシューメン 700、親子丼 650 / カツ丼 900、味噌汁 40 / 豚汁 160 kcal）ので、利用者が正しい候補を選べることに意味があります。

## 🔍 技術選定の理由

### Next.js + FastAPI
当初は Streamlit で UI を組んでいたが、独自デザイン（背景ぼかし・カード UI・グラデーションボタンなど）を作り込むにつれて Streamlit のコンポーネント制約と CSS のせめぎ合いが大きくなったため、React ベースの Next.js に移行。
AI 推論部分は FastAPI の `/predict` エンドポイントとして切り出し、フロントエンドとバックエンドを分離した構成にした。

### MobileNetV2（転移学習）
料理画像の分類には画像認識に特化した CNN が必要だが、ゼロから学習させるにはデータ量・計算コストともに現実的でない。
MobileNetV2 は ImageNet で事前学習済みのモデルの中でも軽量で、Google Colab の無料 GPU 環境でも現実的な時間でファインチューニングが完了する。軽量なため、メモリ 512MB の Render 無料プランでも推論サーバーを動かせる。
また `.keras` 形式での保存・読み込みが Keras と自然に統合されており、デプロイ時の扱いやすさも選定理由のひとつ。

### TensorFlow / Keras
Python の機械学習フレームワークとして最も情報量が多く、トラブル時に参照できるドキュメント・事例が豊富。
Keras の高レベル API により、モデル構築・コンパイル・学習の記述がシンプルに書けるため、学習コードの可読性を保てた。

### Google Colab
GPU を無料で利用できる環境として採用。
MobileNetV2 のファインチューニングには GPU が実質必須であり、ローカル環境に依存せずにどこでも学習を再実行できる点も利点。
Google Drive との連携でデータセットの管理・モデルの保存も容易に行える。

### UECFOOD100
日本食を中心とした 100 クラスの食品画像データセット。
国内での利用を想定したアプリのため、和食を中心に収録しているデータセットを優先して選定した。

## 🤖 AIモデルの仕組み

学習コードは [`train.py`](train.py)（以下はその構成）。

### アーキテクチャ：CNN（畳み込みニューラルネットワーク）

```
入力画像（bb_info.txt の矩形で料理部分を切り出し → 224×224 px）
    ↓
データ拡張（RandomFlip(水平) / RandomRotation(0.05) / RandomZoom(0.2) / RandomContrast(0.2)）
    ↓
Rescaling（0〜1 → -1〜1）
    ↓
MobileNetV2（ImageNet 事前学習済み）
  └─ 最初の 100 層はフリーズ
  └─ 101 層目以降をファインチューニング（BatchNormalization 層はフリーズのまま）
    ↓
GlobalAveragePooling2D
    ↓
Dropout (0.3)
    ↓
Dense → Softmax（100クラス分類）
```

### 学習の工夫
- **料理部分の切り出し**：UECFOOD100 は定食のトレーなど複数の料理が写った画像が多く、同じ画像ファイルが複数のクラスフォルダに置かれている。フォルダ単位で読むと同じ画像に別々の正解ラベルが付くため、各フォルダの `bb_info.txt` にある矩形（外側に 8% の余白を付ける）で該当料理を切り出してから学習する
- **元画像単位での分割**：同じ写真から切り出した矩形が訓練側と検証側に分かれると精度を過大評価するため、元画像単位で訓練 8 : 検証 2 に分ける（`SEED=123`）
- **2段階学習**：
  1. 第1段階：MobileNetV2 を全層フリーズし、追加したヘッドだけを学習（学習率 1e-3、10エポック）
  2. 第2段階：最初の 100 層より後ろを解凍してファインチューニング（学習率 1e-5、最大50エポック）。BatchNormalization 層は、小さなバッチで移動平均が上書きされないよう解凍しない
- **損失関数**：Categorical Crossentropy（label smoothing 0.1）
- **クラス重み付け**：クラスごとの枚数の偏りを補正するため、枚数の少ないクラスの損失を重くする
- **早期停止 (EarlyStopping)**：val_accuracy が 8 エポック改善しなければ停止し、最良時点の重みに戻す
- **学習率の自動調整 (ReduceLROnPlateau)**：val_loss が 3 エポック改善しなければ学習率を 0.3 倍にする
- **モデルチェックポイント**：最良の val_accuracy のモデルを保存

`train.py` には比較用のオプションもある（`--no-crop`：切り出しなしで画像全体を学習、`--include-full`：1皿だけ写った画像は画像全体も学習に加える、`--tag`：比較用モデルを本番モデルと別名で保存 など）。

## 📊 精度の実測と検証の経緯

### 実測値（現在デプロイしている本番モデル）

いずれもアプリと同じ TTA（6パターン、下記「推論の仕様」を参照）で測定。本番モデルは 2026-11-13 に、`train.py` を変更せずに学習し直したモデルへ差し替えた。

| 評価セット | Top-1 | Top-3 | 判定不能率 |
|---|---|---|---|
| 切り抜き検証 2,948件（UECFOOD100 の未学習側、`SEED=123` 分割） | 79.2% | 92.4% | 5.4% |
| Web収集の実写 72枚（24クラス×3枚） | 59.7% | 75.0% | 12.5% |
| Food-101 test から作った評価セット 420枚（21クラス×20枚、海外のWeb写真） | 48.6% | 69.8% | 14.0% |

差し替え前のモデルは、同じ順に Top-1 77.8% / 52.8% / 47.1%、Top-3 92.0% / 75.0% / 67.1%、判定不能率 4.9% / 9.7% / 12.6% だった。

### 検証で分かったこと

- **学習データと実際の写真の差が主な課題**：学習データと同じ撮り方の検証では約79%だが、実写では49〜60%に下がる
- **構図は原因ではなかった**：差し替え前のモデルで、実写72枚を料理の領域に切り抜いて測り直しても 52.8% のまま変わらなかった（改善2枚・悪化2枚）
- **改良版レシピ（v2）の失敗と原因の特定**：明るさ・平行移動の拡張を追加し、料理全体が写った画像も学習に加えた v2 は、切り抜き検証 57.6%、実写 23.6% と大きく悪化した。原因を調べたところ、RandomBrightness の値域指定の誤りで、学習画像の 51.1% が真っ黒、46.3% が白飛びになっていた（実画像1,000枚で測定）。値域を (0,1) に直すと両方 0% になり、修正版（v3）は切り抜き検証 77.6% まで回復した
- **再学習したモデルとの比較と差し替え**：`train.py` を変更せずに学習し直したモデルは、3つの評価セットすべてで差し替え前のモデルの Top-1 を上回った（上の表）。ただし Food-101 420枚での差は、同じ画像でのペア比較（McNemar 検定）で 21勝15敗、p≈0.32 で、統計的に意味のある差ではない。悪化していないことを確認したうえで、このモデルに差し替えた
- **評価セットの作り直し**：72枚の評価セットは誤差が ±11ポイント（95%）あり判断に使えなかったため、Food-101 から 420枚の評価セットを新設した（±2〜3ポイントの差を検出できる）
- **追加データ候補の調査**：
  - UECFOOD256 はクラス1〜100が UECFOOD100 と全14,361ファイルで同一で、新規画像は0枚だった
  - Food-101 は UECFOOD100 との重複が0件（101,000枚を SHA-256 で全数照合）
- **苦手な例**：ラーメンとチャーシューメン、味噌汁・豚汁・けんちん汁、親子丼とカツ丼の混同

### 今後の課題（未実施）

- 実際の利用場面に近い実写データ（スマホで撮った料理写真など）を学習に追加し、学習データと実写の差を縮める
- 混同しやすい料理（ラーメン／チャーシューメン、味噌汁／豚汁／けんちん汁、親子丼／カツ丼）の判別を改善する
- 今後モデルを入れ替えるときは、420枚の評価セットでのペア比較と、スマホで撮った実写での比較で判断する

## 🚀 セットアップ & 起動

スマホのカメラ機能（`getUserMedia`）はHTTPS必須のため、開発用の自己署名証明書を使って両サーバーをHTTPSで起動します。

### 0. 開発用証明書の作成（初回のみ）

```bash
mkdir certs && cd certs
openssl req -x509 -newkey rsa:2048 -keyout key.pem -out cert.pem -days 825 -nodes \
  -subj "/CN=aisystem-dev" \
  -addext "subjectAltName=DNS:localhost,IP:127.0.0.1,IP:<自分のPCのLAN IP>"
```

`certs/`はコミット対象外（`.gitignore`済み）です。LAN IPが変わったら作り直してください。

### 1. バックエンド（FastAPI）

```bash
cd backend
pip install -r requirements.txt
uvicorn api:app --host 0.0.0.0 --port 8000 --ssl-keyfile ../certs/key.pem --ssl-certfile ../certs/cert.pem
```

`https://localhost:8000` でAPIが起動します（`--host 0.0.0.0`でLAN内の他端末からもアクセス可能）。

### 2. フロントエンド（Next.js）

```bash
cd frontend
npm install
npm run dev
```

`npm run dev`は`--experimental-https`付きで`../certs`の証明書を使うよう設定済みです。ブラウザで `https://localhost:3000` を開きます（自己署名証明書のため警告が出た場合は「詳細設定」から進んでください）。

同じWi-Fi内のスマホからは `https://<PCのLAN IP>:3000` でアクセスできます。バックエンドの接続先はアクセス元ホスト名から自動判定されます（固定したい場合は `frontend/.env.local` の `NEXT_PUBLIC_API_URL` を設定）。

スマホなどLAN内の端末からアクセスする場合は、`frontend/.env.local` に `DEV_LAN_HOST=<自分のPCのLAN IP>` を設定してください（Next.jsの開発サーバーが安全のため未許可のホストからのアクセスをブロックするため）。

### 3. モデルの学習（任意）

```bash
python train.py --data-dir ~/datasets/UECFOOD100
```

学習後、`backend/food_model.keras` と `backend/class_ids.txt` が更新されます（`--tag` を付けると別名で保存）。

## ⚙️ 推論の仕様

- 入力画像を **224×224 px** にリサイズ（学習時と同じ BILINEAR 補間）し、0〜1 に正規化
- **TTA（Test-Time Augmentation）**：1枚の画像から **中央ズーム3段（1.0 / 0.9 / 0.8）× 水平反転の有無 = 6パターン** を作って推論し、予測確率を平均する（学習時のデータ拡張にある反転・ズームに合わせた変換）
  - メモリ 512MB の Render 無料プランで動かすため、切り出す前に長辺を 640px まで縮め、6枚を2枚ずつに分けて推論する
- 次のどちらかに当てはまる場合は「**判定不能**」とし、カロリーは表示しない（候補 TOP3 は表示する）
  - 1位の確信度が **10% 未満**
  - 1位と2位の確信度の差が **3ポイント未満**
- 判定できた場合は、料理名で `food_calories.csv` を検索してカロリー・目安量を表示
- **AIの予測候補 TOP3** を、それぞれのカロリー・目安量付きで返す。画面では候補をタップして料理を確定できる（上記「主な機能」を参照）

## 📝 注意事項

- カロリー値はあくまで**目安**です。実際の量・調理法により大きく変わります。
- 実写での精度は Top-1 約49〜60%、Top-3 約70〜75% です（上記「精度の実測と検証の経緯」を参照）。1位の結果が違う場合は、候補 TOP3 から選び直してください。
- モデルは対応料理100種のいずれかを必ず出力します。対応していない料理は、確信度や1位と2位の差が基準を下回れば「判定不能」になりますが、そうでなければ別の料理名で表示されます。
- 学習データ（UECFOOD100）は日本食が中心です。海外のWeb写真で作った評価セット（Food-101）では Top-1 48.6% でした。

## 👤 開発者・担当

大学の授業（週3コマ×2ヶ月間、4人チーム）で「教師あり学習を用いること」を条件とした開発課題として制作。メンバー全員が日常的にカロリーを気にしていたことから、料理の写真を撮るだけでカロリーが分かるアプリを企画・開発した。

### 担当箇所

- **AIモデルの学習・実装**
  - 推論時にTTA（Test-Time Augmentation）を実装し、1枚の画像を6パターン（中央ズーム3段×水平反転）に変換して予測を平均する。変換は学習時のデータ拡張に含まれるものに合わせた
  - 確信度10%未満、または1位と2位の差が3ポイント未満の場合は「判定不能」と表示するなど、実用性を意識した設計
